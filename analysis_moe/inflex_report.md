# Inflex 负载均衡算法报告

## 1. 算法概述

Inflex（Informed Load Balancing）是一种基于探测包的每跳负载均衡算法，通过实时监控本地发送队列和远端接收队列来做出路径选择决策。

### 1.1 核心机制

**探测包机制**
- 每20微秒发送一次探测包
- 探测包携带发送端口的接收队列长度信息
- 探测包在每一跳被更新并转发，形成全路径可见性

**路径选择公式**
```
TotalQueue = localTxQueue × 0.8 + remoteRxQueue
```
- `localTxQueue`: 本端口的发送队列长度（字节数）
- `remoteRxQueue`: 远端端口的接收队列长度（通过探测包获取）
- 权重系数0.8：平衡本地队列和远端队列的影响

### 1.2 选路策略

Inflex在每一跳独立做出路径选择决策：

| 交换机类型 | 决策位置 | 候选路径 |
|-----------|---------|---------|
| ToR交换机 | 上行到Agg | 多条上行链路 |
| Agg交换机 | 下行到ToR | 多条下行链路 |
| Agg交换机 | 转发到Core | 多条上行/下行链路 |
| Core交换机 | 转发到Agg | ECMP多路径 |

**选择逻辑**：选择`TotalQueue`最小的端口转发数据包。

### 1.3 探测包格式

探测包使用`QueueMonitorHeader`封装，包含：
- `m_senderRxQueueLen`: 发送端口的接收队列长度
- `m_queueInfo`: 路径上各跳的队列信息记录

## 2. 拓扑结构

### 2.1 网络拓扑

```
Fat-Tree (k=16, 5-Pod变体)
├── 5个Pod
│   ├── 每Pod: 16台ToR交换机
│   ├── 每Pod: 16台Agg交换机
│   └── 每Pod: 256台主机 (总计1280台主机)
└── Core层: 16台核心交换机
```

**链路配置**：
- 链路速率: 100 Gbps
- 交换机端口队列: 8 MB (2048个64B包)

### 2.2 分组结构

为模拟多网卡主机，采用4节点分组结构：

| 参数 | 值 |
|-----|---|
| 每组节点数 | 4 |
| 总组数 | 320 |
| 每Pod组数 | 64 |
| 每组内节点 | 同Pod内连续4个节点 |

**分组分布**：
- 256个专家组（分布在5个Pod中）
- 8个接收组（从非专家组中选择）
- 56个剩余组（用于背景流）

## 3. 流生成方式

### 3.1 流类型

#### 专家流 (MoE Flows)
- **数量**: 16,384条
- **大小**: 8 KB
- **轮数**: 8轮
- **每轮**: 2,048条流
- **PG标记**: 2 (DRILL/Inflex优先级)
- **发送者**: 256个专家组 × 4节点 = 1,024个源节点
- **接收者**: 每轮随机选择2个接收组

#### 背景流 (Background Flows)
- **大小**: 8 MB
- **PG标记**: 1 (ECMP/feCMP优先级)
- **源节点**: 仅从剩余56组(224节点)中选择
- **目的节点**: 仅从剩余节点中选择
- **数量配置**: 0 / 64 / 128 / 192

### 3.2 时间安排

```
时间轴:
2.000s  ─→ 背景流开始
2.001s  ─→ 专家流开始
每100us  ─→ 下一轮专家流
```

### 3.3 流量比例

| 配置 | 背景流数 | 背景流量 | 专家流量 | 背景占比 |
|-----|---------|---------|---------|---------|
| Hybrid/Inflex(0) | 0 | 0 MB | 128 MB | 0% |
| Hybrid/Inflex(64) | 64 | 512 MB | 128 MB | 80% |
| Hybrid/Inflex(128) | 128 | 1024 MB | 128 MB | 89% |
| Hybrid/Inflex(192) | 192 | 1536 MB | 128 MB | 92% |

| 中负载(128) | Hybrid | 498 | 507 | 868 |

- 低负载下Inflex略优于Hybrid（~1%）

## 5. 算法特点总结

### 5.1 Inflex优势

1. **实时感知**: 通过20μs高频探测快速响应网络状态变化
2. **全局视野**: 每跳决策同时考虑本地发送队列和远端接收队列
3. **高负载表现优**: 在拥堵场景下性能提升更明显（3.4%）
4. **超时更少**: 总超时数比Hybrid少2%

### 5.2 设计权衡

| 方面 | 说明 |
|-----|------|
| 探测开销 | 每20μs发送探测包，增加少量控制流量 |
| 队列占用 | 为获取远端信息，容忍更高的瞬时队列 |
| 复杂度 | 需维护远端队列长度状态，但比多路径选路简单 |

### 5.3 与Hybrid的主要区别

| 特性 | Hybrid | Inflex |
|-----|--------|--------|
| 负载感知 | 本地队列 | 本地队列 + 远端队列 |
| 探测机制 | 无 | 主动探测(20μs间隔) |
| 选路范围 | 静态配置 | 每跳动态决策 |
| 高负载FCT | 基准 | **优3.4%** |

---

## 6. 结论

Inflex负载均衡算法通过探测包机制实现了对网络状态的实时感知，在高负载场景下相比Hybrid算法有3.4%的FCT性能提升。其核心创新在于同时考虑本地发送队列和远端接收队列，使得路径选择更加全局化。

该算法适合于对延迟敏感、流量波动较大的数据中心场景，特别是在多租户、混合流量环境下能够提供更稳定的服务质量。
