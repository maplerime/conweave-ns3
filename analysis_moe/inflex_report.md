# Inflex 负载均衡算法报告

## 1. 算法概述

Inflex（Informed Load Balancing）是一种基于探测包的每跳负载均衡算法，通过实时监控本地发送队列和远端接收队列来做出路径选择决策。

### 1.1 核心机制

**探测包机制**
- 当端口队列超过15KB（单PG阈值）或端口队列使用率超过60%时触发探测
- 探测包携带发送端口的接收队列长度和PFC计数信息
- 探测包最大有效期为10μs，过期信息将被丢弃
- 仅在Inflex模式(lb_mode=12)下启用探测机制

**路径选择公式**
```
pathCost = localTxQueue + (remoteRxQueueLen × 6) / 5 + remotePfcCount × 1024
```
- `localTxQueue`: 本端口的发送队列长度（字节数）
- `remoteRxQueueLen`: 远端端口的接收队列长度（通过探测包获取，权重1.2）
- `remotePfcCount`: 远端端口的PFC计数（权重1024）
- 设计理念：远端队列权重略高，更关注下游拥塞状况；PFC计数反映严重拥塞

### 1.2 选路策略

Inflex采用DRILL风格的Per-Destination粘滞性+随机采样策略：

| 交换机类型 | 决策位置 | 候选路径 | 采样策略 |
|-----------|---------|---------|----------|
| ToR交换机 | 上行到Agg | 多条上行链路 | 缓存+2个随机端口 |
| Agg交换机 | 下行到ToR | 多条下行链路 | 缓存+2个随机端口 |
| Agg交换机 | 转发到Core | 跨Pod转发 | 缓存+2个随机端口 |
| Core交换机 | 转发到Agg | ECMP多路径 | ECMP |

**选择逻辑**：
1. 检查目标地址是否有缓存的最优端口
2. 若有缓存，计算其pathCost作为初始最优值
3. 随机选择2个端口（排除已缓存的端口）
4. 计算这2个端口的pathCost
5. 选择pathCost最小的端口，并更新缓存

### 1.3 Tag机制

| Tag值 | 含义 | 负载均衡方式 |
|-------|------|-------------|
| 0 | 默认 | 同Tag=2 |
| 1 | 背景流 | ECMP（大流，8MB） |
| 2 | 专家流 | Inflex/DRILL（小流，8KB） |

在Hybrid和Inflex模式下，根据Tag区分流量类型并使用不同的负载均衡策略。

为模拟多网卡主机，采用4节点分组结构：

| 参数 | 值 |
|-----|---|
| 每组节点数 | 4 |
| 总组数 | 320 |
| 每Pod组数 | 64 |
| 每组内节点 | 同Pod内连续4个节点 |

**分组分布**：
- **256个专家组**：从320组中随机选择
- **8个接收组**：从剩余64组中随机选择
- **56个剩余组**：用于背景流源和目标

## 3. 流生成方式

### 3.1 流类型

#### 专家流 (MoE Flows)
- **数量**: 16,384条
- **大小**: 8 KB
- **轮数**: 8轮
- **每轮**: 2,048条流 (256专家组 × 8目标组 × 1条流)
- **PG标记**: 2
- **Tag**: 2 (Inflex/DRILL优先级)
- **发送者**: 256个专家组 × 4节点 = 1,024个源节点
- **接收者**: 8个接收组 × 4节点 = 32个目标节点
- **打流模式**: 按组内节点序号一一对应
  - 轮0: 专家组节点[0] → 接收组节点[0]
  - 轮1: 专家组节点[1] → 接收组节点[1]
  - 轮2: 专家组节点[2] → 接收组节点[2]
  - 轮3: 专家组节点[3] → 接收组节点[3]
  - 轮4-7: 重复轮0-3模式

#### 背景流 (Background Flows)
- **大小**: 8 MB
- **PG标记**: 3
- **Tag**: 1 (ECMP优先级)
- **源节点**: 仅从剩余56组(224节点)中选择
- **目的节点**: 仅从剩余56组节点中选择
- **数量配置**: 0 / 64 / 128 / 192
- **约束**: 源节点 ≠ 目标节点

### 3.2 时间安排

```
时间轴:
2.000s  ─→ 背景流开始
2.001s  ─→ 专家流开始
每100us  ─→ 下一轮专家流
```

## 5. 算法特点总结

### 5.1 Inflex优势

1. **实时感知**: 通过探测包获取远端队列信息，更全面了解网络状态
2. **全局视野**: 每跳决策同时考虑本地发送队列和远端接收队列
3. **PFC感知**: PFC计数权重高(1024)，严重拥塞时快速规避
4. **队列控制**: 最大队列长度远低于ECMP/Conweave

### 5.2 设计权衡

| 方面 | 说明 |
|-----|------|
| 探测开销 | 按需触发探测（队列超阈值），开销可控 |
| 远端信息 | 依赖探测包，有10μs有效期限制 |
| 复杂度 | 需维护远端队列长度和PFC计数状态 |
| 适用场景 | 高负载、多跳、非对称拥塞环境 |

### 5.3 与Hybrid的主要区别

| 特性 | Hybrid | Inflex |
|-----|--------|--------|
| 负载感知 | 本地队列 | 本地队列 + 远端队列 + PFC |
| 探测机制 | 无 | 按需探测（队列超阈值触发） |
| 选路策略 | DRILL（基于本地队列） | DRILL + 远端感知 |
| 远端信息权重 | - | remoteRxQueue × 1.2 |
| 拥塞响应 | 本地触发 | 远端PFC优先规避 |

## 6. 结论

Inflex负载均衡算法通过探测包机制实现了对网络状态的实时感知，在当前流量模式下与Hybrid算法性能相当（差异<1%）。相比ECMP和Conweave，Inflex展现出更好的队列控制能力，最大队列长度降低约95%。

该算法的核心创新在于同时考虑本地发送队列、远端接收队列和PFC计数，使得路径选择更加全局化。在非对称拥塞、多跳场景下，远端信息的价值将更加凸显。

**适用场景**：
- 高负载、多跳数据中心网络
- 非对称拥塞环境
- 对队列延迟敏感的应用

**进一步优化方向**：
- 调整远端队列权重（当前1.2）
- 优化探测触发阈值
- 引入自适应权重机制
